# Folio Core ↔ Folio Worker: генерация и размещение

Контракт реализации BellenneOne, 20.10.2026. Публичный префикс — `/folio`.
Оба действия используют существующие `image_jobs`, GET next и POST jobs.
Новой очереди или входящих подключений Core к ПК нет.

## Последовательность

1. Блок «Создать макет» ставит генерацию в `image_jobs`.
2. Воркер получает `action=generate`, сохраняет исходный печатный результат у себя,
   отправляет JPEG-превью и путь `print_file`.
3. «Отправить макет» отправляет **превью**, не печатный файл.
4. Положительный ответ в блоке «Согласовать макет» закрепляет ID последнего
   отправленного задания генерации. Отказ/таймаут не являются согласованием.
5. Блок «Передать заказ вебхуком» отправляет исходный JSON в MES.
   Без согласования выбранного макета отправка блокируется.
6. MES принимает заказ и возвращает `external_order_id`, `print_files`.
7. Core сохраняет их и назначает фазу размещения того же `image_jobs`.
8. Только отчёт об успешном размещении **всех** экземпляров означает завершённое размещение.

Core не читает, не копирует, не переименовывает печатные файлы и не проверяет
их наличие на удалённом диске. Проверки размера/хеша — сведения, сообщённые воркером.
Принятие MES, состояние генерации, согласование и размещение независимы.
Сценарный блок MES переходит дальше после принятия MES; он не означает завершение размещения.

## Авторизация и идентичность

Для GET next и POST jobs:

```http
Authorization: Bearer <общий ключ из настроек Folio>
X-Folio-Worker-Id: 11111111-1111-4111-8111-111111111111
X-Folio-Session-Id: 22222222-2222-4222-8222-222222222222
```

- `X-Folio-Worker-Id`: постоянный UUID установки Windows-воркера. Генерируется
  один раз и хранится в его рабочей папке. Не менять при перезапуске и не
  копировать на ПК без доступа к тем же исходным результатам.
- `X-Folio-Session-Id`: UUID единственного исполняющего процесса/сессии.
  Оба заголовка обязательны для нового двухэтапного протокола.
- `worker_id` внутри задания — **исторический ID задания генерации**, не ID ПК.
- Общий Bearer-ключ аутентифицирует доверенный парк воркеров; ID установки
  маршрутизирует задания, но не является отдельной криптографической учётной записью.
- Дополнительные заголовки моделей/провайдера не требуются.

Старый клиент без обоих ID может выполнять только незакреплённую генерацию.
Размещение ему не выдаётся. Для старых завершённых задач без `owner_id` Core
показывает ошибку владельца, не выбирает случайный ПК и не генерирует заново.
Старые согласования автоматически не восстанавливаются из текста/времени:
требуется явное согласование нужной версии через сценарий.

## Опрос

```http
GET /folio/image-worker/next
```

204: доступного действия нет. 200: JSON одного действия.
401: неверный ключ. 422: некорректные UUID заголовков. 503: ошибка конфигурации.
Сначала выдаётся доступное размещение владельцу, затем генерация.

### Генерация

```json
{
  "action": "generate",
  "id": 123,
  "worker_id": "33333333-3333-5333-8333-333333333333",
  "prompt": "Подготовить портрет",
  "model": "seedream-5-0-lite",
  "prompt_mode": "vision",
  "width_cm": 40,
  "height_cm": 60,
  "image_urls": ["https://one.example.ru/folio/image-worker/input/<token>/0"]
}
```

1–8 HTTPS-ссылок в порядке брифа; `prompt_mode` — `direct` или `vision`.
Core закрепляет установку-владельца при первой выдаче. Повторный опрос возвращает
тот же ID/worker_id; другой установке закреплённое задание не выдаётся.
Воркер обязан вести устойчивый журнал по этим ID и блокировку своего процесса:
повтор получения не означает новый платный запрос. `unknown` не выдаётся на новую генерацию.

Скачивание: `GET /folio/image-worker/input/{token}/{index}`, 200 + изображение,
404 при недоступности. Ссылка содержит секретный токен, не публиковать её в журналах.

### Отчёт генерации

```http
POST /folio/image-worker/jobs/123
Content-Type: multipart/form-data; boundary=...
Authorization: Bearer <ключ>
X-Folio-Worker-Id: 11111111-1111-4111-8111-111111111111
X-Folio-Session-Id: 22222222-2222-4222-8222-222222222222
```

Поля: `worker_id`, `status`.
Статусы: `queued`, `generating`, `composing`, `completed`, `failed`, `unknown`.

- `completed`: `print_file` — путь к **исходному результату** JPG/JPEG на ПК;
  `preview` — загруженный JPEG, ровно 1000 px по длинной стороне, максимум 10 MiB.
  `preview` не содержит зеркальных/белых полей. Печатный источник сохраняет их и 150 DPI.
- `failed`/`unknown`: непустой `error`.
- Успех: 200 `{"ok":true}`. Повтор терминального статуса безопасен;
  изменение терминального исхода — 409. Неверный результат — 422,
  неизвестное задание — 404, другой владелец — 409.
- `completed` означает готовность источника и превью, **не размещение в производстве**.
  На этапе генерации печатный источник хранится в рабочей папке воркера.
  В конечную папку производства он попадает только по `place_print_files` после MES.
  Хранить исходный результат до завершения размещения; срок последующей очистки этим контрактом не задаётся.

## Принятие MES

200/202:

```json
{
  "accepted": true,
  "duplicate": false,
  "external_order_id": "123",
  "print_files": [
    {"serial": 1, "instance_code": "copy-1", "layout_key": "art-1", "filename": "art-1.png"},
    {"serial": 2, "instance_code": "copy-2", "layout_key": "art-2", "filename": "art-2.png"}
  ]
}
```

Число элементов равно `quantity`. Serial — уникальные положительные целые;
instance_code и filename уникальны (имена без учёта регистра).
Строки непустые, до 255 символов; layout_key совпадает с именем без последнего расширения.
Пути, управляющие символы, зарезервированные имена Windows недопустимы.
Весь print_files сохраняется без потери дополнительных полей; максимум 64 KiB.

Некорректный/отсутствующий print_files: MES может быть принято, но размещение
**не назначается**. В UI ошибка и ручной повтор запроса MES с прежними JSON/Idempotency-Key.
Имена не придумываются. Изменившиеся уже сохранённые имена/ID MES требуют сверки.
В исходном вебхуке `print_file.filename` остаётся именем источника воркера:
ответ MES не изменяет payload, UUID события или исходный путь.

## Действие размещения

Тот же GET next:

```json
{
  "action": "place_print_files",
  "id": 123,
  "worker_id": "33333333-3333-5333-8333-333333333333",
  "worker_instance_id": "11111111-1111-4111-8111-111111111111",
  "item_id": 42,
  "layout_version": "opaque-preview-media-id",
  "operation_id": "44444444-4444-4444-8444-444444444444",
  "claim_token": "55555555-5555-4555-8555-555555555555",
  "lease_until": "2026-10-20T12:10:00+00:00",
  "external_order_id": "123",
  "source_print_file": "D:\\Results\\original.jpg",
  "destination": {"kind": "worker_print_directory"},
  "print_files": [
    {"serial": 1, "instance_code": "copy-1", "layout_key": "art-1", "filename": "art-1.png"},
    {"serial": 2, "instance_code": "copy-2", "layout_key": "art-2", "filename": "art-2.png"}
  ],
  "results": {},
  "pending_serials": [1, 2]
}
```

- `id` — ID image_jobs; `layout_version` — неизменяемый ID JPEG-превью
  согласованной версии (не версия графа сценария).
- `operation_id` — UUID события MES; одна операция на согласованный результат.
- `destination.kind=worker_print_directory` — использовать **существующую выбранную
  на воркере локальную/UNC-папку печатных файлов**. Core не задаёт новый путь.
  Если папка недоступна — ошибка файла, не произвольная резервная папка.
- Писать только `pending_serials`, точно с именами MES. `print_files` всегда полный список.
- Если расширение MES отличается от формата источника, воркер должен корректно
  кодировать результат в указанный формат, сохранив печатные размеры/поля/DPI.
  Переименовывать JPEG в `.png` без конвертации запрещено. Неподдерживаемый формат — ошибка файла.

### Захват, параллельность и перезапуск

Выдача атомарна (`BEGIN IMMEDIATE`). Lease — 600 секунд.
Повтор GET той же установки и сессии возвращает тот же claim_token и продлевает lease.
Другой сессии действующий захват не выдаётся. После истечения новый захват
получает новый token; отчёты старого token отклоняются.
`finished` завершает попытку. Следующая попытка после partial получает новый
token даже в той же сессии; ранее успешные экземпляры остаются в results.

Воркер продлевает lease опросом или отчётом `running` до истечения,
прекращает запись при потере lease. Перед атомарным размещением проверяет актуальность захвата.
Core не может физически остановить запись на удалённом Windows-ПК:
локальная блокировка процесса/операции и файловый журнал обязательны на воркере.

Воркер хранит manifest `(operation_id, layout_version, serial, filename, hash, path)`.
При потере ответа не копирует вслепую: сверяет существующий файл со своим manifest
и повторяет отчёт. Чужой/отличающийся файл не перезаписывает.
Временный файл и атомарное переименование выполняются **воркером**, не Core.
После перезапуска можно восстановить session UUID только если старый процесс точно
остановлен; иначе новая сессия ждёт истечения lease и получает новый token.

## Отчёт размещения

Тот же POST jobs, но **application/json**, с теми же тремя заголовками:

```json
{
  "action": "place_print_files",
  "operation_id": "44444444-4444-4444-8444-444444444444",
  "layout_version": "opaque-preview-media-id",
  "claim_token": "55555555-5555-4555-8555-555555555555",
  "status": "finished",
  "files": [
    {
      "serial": 1, "filename": "art-1.png", "status": "completed",
      "saved_path": "\\\\production\\prints\\art-1.png",
      "size_bytes": 123456, "sha256": "aaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaa"
    },
    {"serial": 2, "filename": "art-2.png", "status": "failed", "error": "Нет доступа к папке"}
  ]
}
```

До 64 KiB. `status`: `running` (прогресс/продление) или `finished` (попытка окончена).
`files` может содержать часть результатов или быть пустым для heartbeat.
У файла `completed` обязательны serial, filename и saved_path с тем же именем.
size_bytes (положительное целое) и sha256 (64 hex-символа) необязательны, но желательно присылать.
У `failed` обязателен непустой error (сохраняется до 1000 символов).

200:

```json
{
  "ok": true,
  "placement_state": "partial",
  "results": {
    "1": {"serial": 1, "filename": "art-1.png", "status": "completed", "saved_path": "\\\\production\\prints\\art-1.png", "size_bytes": 123456, "sha256": "aaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaa"},
    "2": {"serial": 2, "filename": "art-2.png", "status": "failed", "error": "Нет доступа к папке"}
  }
}
```

Состояния фазы: `pending`, `running`, `partial`, `completed`, `stale`.
`finished` с неуспешными/отсутствующими экземплярами → partial, следующий опрос
выдаёт оставшиеся не раньше чем через 60 секунд. Успешные результаты сохраняются
в БД и переживают перезапуски; не заменяются ошибкой или другим путём/хешем.
Повтор идентичного отчёта безопасен. Все экземпляры completed → completed.

401 — неверный ключ; 413 — слишком большой отчёт; 409 — неверное тело,
истёкший/чужой захват, другая версия, отменённый заказ или попытка изменить успех.
При 409 не продолжать запись, повторить опрос. При сетевом сбое повторять тот же
отчёт, не перезапускать генерацию.
Если новый макет отправлен вместо согласованного, согласование сброшено или заказ
отменён, выдача прекращается; следующий опрос помечает фазу stale, старый отчёт отвергается.

## Обновление

Обновить Core API и фоновый процесс, затем Windows-воркер по этому контракту.
Схема БД расширяется при запуске; старые задания и события не переотправляются массово.
Существующие сценарии должны содержать ветку:
Создать макет → Отправить макет → Согласовать макет (положительная ветка) → MES.
Новая генерация вместо недоступного исходника размещения не запускается.

Необходимо реализовать новый модуль экосистемы Bellenne:

BellenneParity

Назначение модуля:

BellenneParity ежедневно получает информацию о товарах и ценах из Wildberries и Ozon, сопоставляет одни и те же товары между маркетплейсами, сохраняет историю цен и показывает расхождения.

Основная задача системы:

быстро ответить на вопросы:

- одинаковые ли цены товара на Wildberries и Ozon;
- где цена отличается;
- какой именно тип цены отличается;
- насколько отличается цена в рублях и процентах;
- когда произошло изменение;
- как менялась цена товара со временем.


==================================================
ОБЩИЙ ПРИНЦИП
==================================================

BellenneParity является модулем аналитики и контроля цен.

Он НЕ должен:

- автоматически менять цены на маркетплейсах;
- рассчитывать рекомендуемую цену;
- менять скидки;
- управлять рекламой;
- самостоятельно исправлять расхождения;
- придумывать отсутствующие цены;
- считать отсутствующую цену равной нулю.

На первом этапе приложение только:

получает данные;
нормализует их;
сохраняет историю;
сопоставляет товары;
сравнивает цены;
показывает расхождения.


==================================================
ИНТЕГРАЦИИ
==================================================

Необходимо поддержать:

Wildberries API

Ozon Seller API


Перед реализацией каждого адаптера:

1. Изучить актуальную официальную документацию API.
2. Определить реальные методы получения списка товаров.
3. Определить реальные методы получения цен.
4. Проверить доступные идентификаторы товаров.
5. Проверить, какие виды цен действительно доступны.
6. Проверить rate limits и пагинацию.
7. Проверить формат ошибок API.
8. Не основываться на устаревших примерах из интернета, если они противоречат актуальной документации.


Все marketplace-specific детали должны находиться внутри адаптеров:

WildberriesAdapter

OzonAdapter


Остальная бизнес-логика НЕ должна напрямую зависеть от структуры JSON Wildberries или Ozon.

ТОВАР
==================================================

Для каждого товара необходимо получить минимум:

Seller article является идентификатором продавца.


==================================================
НОРМАЛИЗАЦИЯ ЦЕН
==================================================

Нужно создать единую внутреннюю модель цены.

Минимально поддерживать:

base_price

discount_price

loyalty_price


Где:

base_price
обычная / базовая цена товара до скидок, если площадка действительно предоставляет такое значение.

discount_price
актуальная цена с применяемой скидкой продавца / маркетплейса согласно реально доступному API.

loyalty_price
цена с картой, клубом, программой лояльности или аналогичной программой маркетплейса, если такую цену возможно получить через официальное API.


КРИТИЧЕСКОЕ ПРАВИЛО:

Не считать два price-поля эквивалентными только потому, что они имеют похожее название.

Внутри каждого marketplace adapter явно документировать:

какое API-поле соответствует:

base_price
discount_price
loyalty_price


Если определённый тип цены маркетплейс не предоставляет:

хранить:

null

и статус:

unavailable

а не копировать другую цену.


Желательно сохранять:

currency

обычно RUB, но не хардкодить это в доменную модель без необходимости.

==================================================
СОПОСТАВЛЕНИЕ ТОВАРОВ
==================================================

Критически важная часть системы:

нужно определить, какой товар Wildberries соответствует какому товару Ozon.


Основной предполагаемый идентификатор:

артикул продавца.


Но нельзя считать совпадение гарантированным.

Нужно реализовать сущность ProductMapping.


Пример:

Internal Product

→ Wildberries Product

→ Ozon Product


ProductMapping должен позволять:

автоматическое сопоставление по точному seller article;

ручное исправление сопоставления;

ручное создание связи;

отвязку неправильной связи.


Не выполнять fuzzy matching по названию товара автоматически.


Если:

WB article = ABC-123

Ozon offer_id = ABC-123

система может создать автоматическое сопоставление.


Но такое сопоставление должно быть прозрачным и доступным для исправления.


Если найдено несколько кандидатов:

не выбирать случайно.

Статус:

mapping_required.

==================================================
ИСТОРИЯ ЦЕН
==================================================

Для каждого товара хранить историю изменения цен.

Минимальная детализация:

1 snapshot в день после основной ежедневной синхронизации.


Если внутри дня выполняется ручная синхронизация и цена изменилась:

разрешается сохранить дополнительный snapshot.


Не создавать новые строки истории, если абсолютно все нормализованные значения цены совпадают с последним snapshot, если архитектурно это не требуется.

При этом сам факт успешной синхронизации должен фиксироваться отдельно.


==================================================
СИНХРОНИЗАЦИЯ
==================================================

Автоматическая синхронизация:

1 раз в день.


Конкретное время должно быть configurable.

Не хардкодить cron-логику глубоко в бизнес-код.


Также должна быть кнопка:

Sync now


Синхронизация должна:

1. Получить товары WB.
2. Получить цены WB.
3. Нормализовать данные.
4. Получить товары Ozon.
5. Получить цены Ozon.
6. Нормализовать данные.
7. Обновить каталог товаров.
8. Обновить / проверить mappings.
9. Сохранить price snapshots.
10. Пересчитать расхождения.
11. Зафиксировать результат sync job.


Если API одной площадки недоступно:

данные второй площадки всё равно можно сохранить.

Но comparison result не должен выглядеть как достоверное новое сравнение.

==================================================
РАСХОЖДЕНИЕ
==================================================

Расхождение существует, когда:

WB price != Ozon price


для хотя бы одного сопоставимого типа цены.


Но архитектуру сделать так, чтобы позже можно было добавить допустимый threshold.

Например:

50 ₽

или

3%


На первом этапе threshold = 0, если пользователь не настроил иначе.


Не хардкодить сравнение только одной цены.


==================================================
СТАТУСЫ СРАВНЕНИЯ
==================================================

Для товара желательно иметь вычисляемый status:

matched

mismatch

missing_wb

missing_ozon

mapping_required

price_unavailable

stale


matched:

все доступные сравниваемые цены совпадают.


mismatch:

есть хотя бы одно расхождение.


missing_wb:

mapping существует, но WB товар больше не найден / недоступен.


missing_ozon:

аналогично Ozon.


mapping_required:

товар не удалось однозначно сопоставить.


price_unavailable:

товары есть, но необходимых цен недостаточно для сравнения.


stale:

данные одной из площадок устарели относительно установленной политики.

# Архитектура BellenneOne

## Границы приложений

BellenneOne использует модульную архитектуру без слияния ORM-моделей и обработчиков в один процесс:

```text
браузер :17863
       │
       ▼
 nginx gateway ── auth_request ──► Pulse identity/session
       │
       ├── /             ► BellenneOne Shell
       ├── /pulse/       ► BellennePulse
       ├── /echo/        ► BellenneEcho
       ├── /vector/      ► BellenneVector
       ├── /nest/        ► BellenneNest
       └── /proof/       ► BellenneProof Core
```

Такой подход сохраняет проверенную бизнес-логику Pulse и изолирует фоновые задачи, схемы SQLite и внешние API каждого модуля. При этом для пользователя система выглядит как одно приложение на одном порту.

## Единая авторизация

Pulse хранит пользователя и подписанную сессию. Это технический провайдер идентичности, а не оболочка платформы: страницы BellenneOne обслуживает отдельный контейнер `shell`.

Перед доступом к Shell, Pulse, Echo, Vector, административному UI Nest или Proof nginx вызывает внутренний endpoint `/internal/auth`. После успешной проверки шлюз передаёт во внутреннюю сеть:

- `X-Bellenne-User-Id` — стабильный идентификатор аккаунта;
- `X-Bellenne-Username` — имя пользователя;
- `X-Bellenne-Csrf-Token` — токен общего выхода из аккаунта.

Эти заголовки нельзя принимать от внешнего клиента напрямую. Поэтому наружу опубликован только gateway, а контейнеры приложений используют только `expose`.

Echo и Vector сохраняют внешний идентификатор в своих локальных таблицах пользователей. Nest использует его как ключ пользовательской конфигурации, владельца персонального API-токена и фильтр истории. При первом входе существующий единственный локальный аккаунт Echo или Vector автоматически привязывается к единому аккаунту. Если в старой базе Echo несколько пользователей, безопасное автоматическое объединение не выполняется: имя нужного пользователя должно совпадать с именем аккаунта Pulse.

Внешний Nest API является отдельным исключением: `/nest/api/*` не требует браузерной сессии и защищён персональным заголовком `AUTH-TOKEN`. Токен создаётся владельцем в UI Nest, хранится только как digest и определяет аккаунт и его конфигурацию. Заголовок `X-MES-User` передаётся MES и обозначает фактического пользователя, инициировавшего расчёт; он сохраняется в истории, но не участвует в авторизации. Alias `X-Bellenne-Username` поддерживается только для совместимости старых клиентов.

Proof имеет два внешних исключения. `/proof/api/v1/*` защищён индивидуальным токеном Worker в заголовке `X-Proof-Worker-Token`, а `/proof/webhooks/amocrm/*` — индивидуальным webhook secret в URL. Их gateway-настройки намеренно не принимают доверенные пользовательские заголовки извне. Токены и webhook secrets хранятся только как SHA-256 digest, credentials amoCRM — в зашифрованном виде.

## Настройки

`/settings` принадлежит BellenneOne Shell и служит единым маршрутизатором настроек:

- Pulse: кабинеты и API маркетплейсов;
- Echo: кабинеты, шаблоны и автоматизация;
- Vector: API продвижения и расписание сбора.
- Nest: параметры алгоритма, API и история расчётов.
- Proof: Workers, versioned presets, amoCRM и параметры хранения результатов.

Секреты и бизнес-настройки остаются в volume соответствующего модуля. Shell не дублирует их в отдельную базу.

## Маршрутизация

Внутренние приложения получают URL без внешнего префикса. nginx удаляет `/pulse`, `/echo`, `/vector`, `/nest` или `/proof` перед передачей запроса. Шаблоны формируют ссылки с `MODULE_PREFIX`, поэтому формы, статические ресурсы и редиректы остаются внутри своего модуля.

## Proof Core и Workers

Proof Core владеет API, DB-очередью, Jobs, presets, событиями, результатами и внешней доставкой. Proof Worker остаётся отдельным исполнителем и не получает credentials amoCRM. Получение задания выполняется атомарно; heartbeat определяет доступность Worker, а задание зависшего Worker возвращается в очередь при следующем claim.

Processing Status и Delivery Status хранятся и изменяются независимо. Поэтому сбой callback в amoCRM не отменяет уже созданный результат, а `Retry Delivery` не запускает повторную обработку. Preset фиксируется в Job как неизменяемый JSON snapshot с logical ID и версией. Результаты разных попыток не перезаписываются.

Mattermost подключается через Incoming Webhook, URL которого хранится в зашифрованных credentials Proof. События уровней Error и Critical после commit создают отдельную запись notification outbox. Отправка выполняется вне транзакции Job: сбой Mattermost фиксируется в интеграции и журнале, но не меняет Processing или Delivery state и не создаёт рекурсивное уведомление.

## Хранилища и резервное копирование

SQLite-файлы нельзя копировать во время записи обычной файловой командой. Перед резервным копированием или миграцией остановите gateway и продуктовые контейнеры. Скрипт `scripts/migrate-existing-data.ps1` создаёт резервную копию целевых volumes до замены файлов. Для Proof резервируйте volume `proof_data` целиком: в нём совместно находятся SQLite и каталог файлов результатов, и они должны восстанавливаться одной согласованной версией.

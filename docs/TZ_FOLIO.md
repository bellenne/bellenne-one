# Техническое задание: BellenneFolio

**Версия:** 1.1 — проект ТЗ, не утверждённые решения перечислены в конце.  
**Цель:** система первичного сопровождения заказов «картина по фото» на Ozon с настраиваемым конструктором диалогов, единым окном чатов, сохранением брифа и простым RBAC.  
**Документы:** `AGENTS.md` → `docs/products/FOLIO.md` → `docs/BRANDBOOK.md`.  
**Принцип:** фактические возможности Ozon и существующего репозитория имеют приоритет над предположениями.

## 1. Бизнес-цель и границы

1. Получать заказы с Ozon через официально доступную интеграцию и выделять товарные позиции, требующие персонализации.
2. Сопоставлять каждую позицию с типом товара и опубликованным сценарием сбора информации.
3. Обрабатывать переписку с покупателем через поддерживаемые чаты Ozon, собирать фотографии/текст/пожелания, контролировать полноту брифа.
4. Давать администратору полный UI для построения этапов, условий и текстов ответов без правки кода.
5. Давать менеджеру единый интерфейс чатов с ручным ответом, просмотром полученных данных и перехватом автоматики в рамках чата.
6. Сохранять полную прослеживаемость действий и ошибок; формировать структурированный результат «бриф готов к следующему этапу».

**Вне scope первой версии:** фактическая художественная обработка, коллажирование, создание картинки по шаблону, производство/печать, отгрузка, изменения Pulse/Echo/Vector/Nest/Proof и интеграция с MES, если она не будет запрошена отдельно.

## 2. Критический предварительный этап — проверка Ozon (Spike 0)

До разработки отправки сообщений исследовать **для конкретного кабинета продавца**:
- вид подписки и доступ к Seller API чатам, чтению/отправке текста, отправке/чтению вложений;
- актуальные версии методов, параметры, пагинацию и ограничения запросов;
- допустимость и ограничения автоматизации переписки согласно действующим правилам Ozon;
- ограничения открытия диалога продавцом в зависимости от схемы заказа (FBO/FBS/rFBS), временные окна и реальную возможность связать чат с позицией/отправлением;
- доступные API заказов, факт и формат обновлений (push, polling или другое), есть ли вообще поддерживаемое событие для новой заявки;
- варианты доставки фото покупателя через API (тип вложения, разрешение доступа, URL/скачивание, срок действия);
- возможность отправки изображений/файлов, если это потребуется; формат и ограничения;
- поведение при отозванном API-ключе, rate limit, недоступном чате, блокировке отправки.

**Выход Spike:** матрица «требование → подтверждённый метод / ограничение / недоступно», сохранённые безопасные примеры запросов/ответов без секретов и адаптированное API-contract описание. При недоступности chat API нельзя выдавать фиктивную реализацию; подготовить ограниченный режим + решение пользователя о дальнейшем пути. Не использовать браузерный скрейпинг как молчаливую замену API.

**Стартовые источники для проверки, не неизменяемый контракт:**
- https://docs.ozon.ru/api/seller/ — официальная актуальная документация;
- https://t.me/s/OzonSellerAPI — уведомления о версиях и изменениях (в частности, v3 chat list/history);
- публичные зеркала описывают `POST /v3/chat/list`, `/v3/chat/history`, `/v1/chat/send/message`, `/v1/chat/send/file`, но версии, подписка и применимость подлежат проверке по официальным данным и тестам текущего кабинета.

## 2.1 Ozon: обязательный UI подключения и проверок

Администратор вводит `Client ID` и `API-ключ` в отдельном экране `Настройки → Ozon` (в первой настройке — шаг 1 мастера), а не в общую форму со сценариями и товарами. У кабинета — понятное имя, Client ID, статус подключения, дата успешной проверки, статус настроенного ключа. Поле ключа password/masked; сохранённое значение **не отдавать** во frontend и не показывать повторно, только «Заменить ключ». Передача TLS, хранение encrypted/secret store по принятой архитектуре, доступ к изменению только admin. Не писать секреты в логи и экспорт.

Разделить действия: `Сохранить` (проверка формата/безопасное сохранение) и `Проверить доступ` (серверный диагностический запрос). Проверка показывает **отдельные** состояния `кабинет / заказы / чтение чатов / отправка сообщений / вложения` по реально проверенным операциям, с `доступно / недоступно / не проверено`; недоказанная возможность не становится «доступно». Методы и права зависят от текущей документации и конкретного кабинета: выполнить Spike 0 и не вшивать предположения о тарифе или кодах ошибок. Отправка тестового сообщения возможна только как отдельная явная функция для подтверждённого тестового чата; проверка подключения сама ничего покупателям не отправляет.

В мастере должна быть связь с этапами сопоставления товаров и публикации сценариев, но экраны остаются самостоятельными. При смене ключа — повторная проверка прав, понятное указание, какие функции недоступны, и явная блокировка автоматизации при критическом отсутствии доступа. Менеджеру этот раздел и endpoints недоступны.

## 3. Товарная модель

| Внутренний код | Название | Что собрать | Условия |
|---|---|---|---|
| `portrait_background` | Картина + замена фона | исходное фото, описание/пример желаемого фона, дополнительные пожелания по сценарию | Фактическую замену фона Folio не выполняет |
| `collage` | Коллаж до 8 фото + текст | вложения, текст надписи, пожелания к коллажу при наличии | максимум 8 фото на товарную позицию, минимум согласовать |
| `template_art` | Обработка по шаблону | исходное фото, ровно один `template_id` из разрешённых шаблонов, пожелания при наличии | никакого автоматического выбора шаблона без утверждённого правила |

Администратор управляет маппингом: кабинет продавца + SKU/offer_id (подтверждённый идентификатор товара) → тип товара → опубликованный сценарий → разрешённые шаблоны, если нужны. Несопоставленный товар уходит на разбор администратору; не угадывать тип по имени. Один заказ может содержать несколько позиций; бриф и прогресс хранятся на уровне позиции, связь чата — отдельная сущность. Если API не позволяет однозначно связать чат с товарной позицией, требуется выбор/подтверждение менеджером, а не автоматическая подмена.

## 4. Сущности и рекомендуемые поля

Рекомендуемая модель (скорректировать под существующую схему):
- `seller_accounts`: идентификатор кабинета, имя, статус подключения, зашифрованные секреты (в защищённом хранилище), время синхронизации;
- `marketplace_orders`: внешний номер заказа/отправления, кабинет, статус Ozon, время создания/обновления, нормализованный контекст;
- `order_items`: внешний item/sku/offer_id, тип, количество/вариант при наличии, ссылка на заказ;
- `product_mappings`: кабинет, идентификатор SKU/offer_id, тип Folio, сценарий, опционально шаблоны;
- `ozon_chats`: внешний chat_id, кабинет, внешний контекст, режим `bot/manual`, assigned_manager (если назначение внедрено), last_message_id, sync state;
- `messages`: внешний message_id (где существует), chat_id, направление, actor, текст/attachment refs, received/sent timestamps, send state;
- `media_assets`: защищённая ссылка на бинарный объект, MIME, размер, checksum, источник и принадлежность позиции;
- `templates`: ID, название, thumbnail/reference, активность, область применимости;
- `scenarios` + `scenario_versions`: тип/назначение, draft/published, схема графа, версия, автор, timestamps;
- `scenario_instances`: привязка к позиции/чату, версия, текущий node, состояние, concurrency version;
- `briefs` + `brief_fields`: заполненные значения по позиции, attachments, completeness, revision, approval/ready metadata;
- `outbound_messages`: outbox entry, idempotency key, state, external result, attempts, last error;
- `integration_events`: source ID/dedup key, payload reference или обезличенные metadata, обработка;
- `audit_events`: actor, action, object, correlation IDs, время, безопасные изменения.

Не хранить API-ключи в открытых полях или экспортируемом JSON. Уникальные ограничения строить по паре `seller_account + external_identifier`; проверить семантику идентификаторов Ozon до миграций. Публикация сценария и создание экземпляра должны быть транзакционными.

## 5. Конструктор бота: требования

### 5.1 UI админа: визуальный node builder (обязателен в первой версии)

**Acceptance requirement:** администратор может создать, изменить, связать, проверить, протестировать и опубликовать сценарий **полностью через видимый интерактивный граф**. Список или последовательная форма сами по себе не считаются выполнением требования; raw JSON/код доступен только разработчику, не обязателен пользователю.

- Экран списка сценариев: имя, тип товара, привязка кабинета/SKU, draft/published, версия, автор, изменён. `Создать`, `Копировать`, `Редактировать`, `Тест`, `История версий` согласно реальным возможностям.
- Редактор: верхний toolbar (название, draft state, unsaved, save, validate, dry-run, publish), слева palette с ограниченными поддерживаемыми узлами, по центру canvas со связями и подписью выходов, справа inspector выбранного узла. Инспектор открывается по выбору, пустое состояние объясняет следующий шаг.
- Реализация графа: визуальное добавление/перемещение/удаление узлов, создание/переподключение/удаление рёбер, drag либо явная команда «Соединить», zoom, pan, fit-to-screen. Позиции и изменения сохранять в draft; показывать несохранённое и подтверждать уход. Не требовать вводить ID. Доступен синхронизированный линейный список шагов для навигации и keyboard accessibility, но основной редактор — схема.
- Обязательные типы, если движок их поддерживает: `Start/Incoming event` (реально подтверждённый триггер заказа/входящего сообщения), `Send message`, `Ask text`, `Ask photo`, `Choice/Select template`, `Condition`, `Wait for reply`, `Human handoff`, `Ready/End`. Не выдумывать самостоятельные каналы, callback или виды событий. В палитре — человекочитаемые названия («Старт», «Отправить сообщение», «Получить фотографию» и т. д.).
- Inspector узла: редактирование текста входящего условия/исходящего сообщения; для `Send message` — многострочный текст; для `Ask text` — вопрос, поле брифа, поддерживаемый валидатор; для `Ask photo` — вопрос, лимит, целевое поле и режим приёма по возможностям Ozon; для `Condition` — проверяемое поле, оператор, значения и подписанные выходы; для handoff — понятный смысл перехода в ручной режим. Показывать только реально доступные поля выбранного типа.
- Templates/variables: whitelist доступных полей с click-to-insert, preview на фикстуре, диагностика неизвестных переменных/лимитов сообщений, никаких произвольных скриптов, неподтверждённых клиентских данных или сгенерированных «обещаний» покупателю.
- Схема и реальные переходы должны иметь **одну модель данных**; canvas не декоративная картинка. Frontend и executor читают одну сериализованную/версионированную структуру; нельзя поддерживать параллельный hardcoded flow.
- Validate перед публикацией: один Start, корректные переходы, допустимые типы, отсутствующие связи/сообщения, достижимость End и обязательных полей, ошибки циклов, отсутствующий SKU mapping/недоступные media capabilities где применимо. Показать счётчик ошибок и список «узел → проблема → как исправить»; клик фокусирует нужный узел. Предупреждения отделить от блокирующих ошибок.
- Dry-run: из UI выбрать тестовый тип товара, подать последовательность тестовых incoming messages/attachments, видеть подсветку текущего узла и trail переходов, итог заполненных полей; ноль запросов отправки в Ozon. Публикация создаёт immutable version и требует подтверждения; активные instances остаются на старой версии.
- Выбор UI-библиотеки графа: после инспекции фактического frontend стека. Разрешена одна подходящая зависимость для node canvas после оценки лицензии, размера и совместимости с существующей Bellenne UI. Не подключать новый глобальный UI-kit только ради графа.

### 5.2 Исполнение

По созданной товарной позиции выбирается опубликованный сценарий; создаётся instance с зафиксированной версией. Входящее событие применяется один раз и к нужному context. `Ask photo` проверяет реальный доступный тип вложения и число принятых фото; неподтверждённый/недоступный файл не считать полученным. `Ask text` валидирует формат/непустоту по настройке. Выбор шаблона — ровно одно значение из разрешённого каталога. Если ответ неоднозначен, не пытаться выдавать догадку за выбор: уточнить либо передать менеджеру. В `ready` переходить только после проверки required fields.

После публикации новые instances используют новую версию; существующие сохраняют старую. Админский механизм принудительной миграции существующих instances — отдельная опция после согласования стратегии; не делать автоматически.

### 5.3 Предлагаемые стартовые шаблоны сценариев

A. Картина + фон: заказ → запрос фото → запрос желаемого фона → необязательные дополнительные пожелания → проверка заполненности → готово либо manager handoff.

B. Коллаж: заказ → запрос фото (не более 8) → запрос текста → уточнение размещения при наличии настройки → проверка заполненности → готово либо handoff.

C. Шаблон: заказ → запрос фото → выбор единственного допустимого шаблона → дополнительные пожелания при наличии настройки → проверка → готово либо handoff.

Подтверждение собранной сводки покупателем — **предлагаемая** настраиваемая опция; включить или исключить после решения пользователя. Не формировать от себя тексты обращений и обещания: тексты подготавливает админ через UI.

## 6. Ozon Inbox и ручные ответы

### 6.1 Интерфейс: чистый мессенджер, не админ-панель

**По умолчанию только две колонки:** чат-лист слева (~280–340px на desktop, адаптивно), справа область переписки максимально широкая. Третья колонка не закреплена: компактный контекст заказа/позиции/прогресса бота открывается по кнопке `Данные заказа` как drawer и закрывается. На узких экранах — переключение список ↔ диалог, контекст отдельным drawer; без сломанной горизонтальной прокрутки.

- Список: поиск по доступным данным, компактные фильтры `Все / Непрочитанные / Требуют менеджера` (только поддерживаемые backend statuses), время, последняя строка, непрочитанное, спокойный indicator `бот/вручную`. Сортировка по последней активности. Не помещать в каждую строку SKU, все поля брифа и технические идентификаторы.
- Заголовок диалога: имя/доступный идентификатор клиента, краткий заказ, текущий режим и одна доступная кнопка takeover/return по правилам. «Данные заказа» открывает drawer с товарной позицией, фото, заполненными полями и текущим шагом. Если несколько позиций — менеджер явно выбирает контекст без автоматического угадывания.
- Переписка: естественные пузырьки/строки с датами и временем, вложения с безопасными thumbnails/viewer, обозначение `Бот` или `Менеджер` у исходящих, сообщение об ошибке/неопределённой отправке локально возле сообщения. Никаких крупных карточек вокруг каждой реплики, технических payloads, полного audit trail или экрана настроек Ozon.
- Composer закреплён снизу: поле ввода, отправка, вложение лишь при подтверждённой поддержке API, блокировка отправки в запрещённых состояниях с понятным пояснением. Не показывать фиктивно отправленные сообщения; pending/sent/failed/unknown различимы.
- Админский аудит, детальный webhook log, настройки ключей, сценарии — отдельные разделы. Manager видит только Чаты + разрешённый контекст заказа, никак не admin navigation.

**UX критерий:** менеджер открывает чат, читает историю, видит какой этап ждёт клиента, переключает в ручное управление и отвечает, не посещая экран настроек и не разбираясь в API.

### 6.2 Поведение

- Исходящее сообщение менеджера отправляет сервер через Ozon adapter, не из браузера напрямую.
- Взятие чата менеджером в работу переключает чат в `manual` атомарно до следующей отправки бота; возвращение `bot` требует явного действия с определением текущего шага.
- Если менеджер ответил на ожидание, нет автоматического «продолжить на всякий случай»; данные сохраняются по заданному правилу, возобновление только после разрешённого перехода.
- UI показывает реальные incoming/outgoing, бота/менеджера и статусы отправки, включая `unknown` при сетевой неопределённости. Перед повторной отправкой сверить историю по возможностям API и предотвратить дубли.
- Синхронизация и чтение не должны менять статус Ozon «прочитано» без заданной политики; решение за администратором/продуктом.
- Отправка фото/файла поддерживается только после подтверждения Ozon API. Вложения покупателя доступны менеджеру по защищённым ссылкам, не публичным бесконтрольным URL.

| Управлять пользователями/ролями | Да | Нет |
| Отдельный список заказов/экспорт всех данных | Да | Нет |

Стартовые роли только `admin` и `manager`; отдельные permissions можно использовать внутри реализации, но не открывать создание произвольных ролей. Backend middleware/policies + тесты на прямые URL, API, вложения и объектные ID. Сессии/аутентификация по принятой инфраструктуре Bellenne, без выдумывания SSO.

## 7.1 Пошаговый onboarding / настройка после подключения

Не делать единую мегa-форму. Wizard админа: `1. Подключение Ozon (Client ID/API key)` → `2. Проверка доступа по capabilities` → `3. Соответствие SKU типам товаров` → `4. Сценарии (visual node builder)` → `5. Симуляция и готовность` → `6. Включение автоматизации`. Вверху прогресс и статусы этапов, на каждом экране объяснение цели и только связанные настройки; кнопки «Назад», «Сохранить», «Продолжить». Не терять draft при переходе; этапы можно открыть позже через раздельные разделы. Нельзя сделать вид, что весь onboarding успешен, если ключ валиден, а API чатов недоступен. Отдельная активация только при подтверждённых минимальных prerequisites.

## 7.2 Понятные ошибки и состояния

Любая ошибка: заголовок на человеческом языке, конкретная сущность/этап, следующий шаг и безопасный `request_id/correlation_id` в раскрываемых деталях админа. Например:
- Не удалось проверить ключ → «Проверьте Client ID и API-ключ»; не утверждать причину без проверенного ответа.
- Кабинет доступен, отправка чатов недоступна → «Проверьте права/подписку или доступность метода».
- Товар не сопоставлен → «Выберите тип и сценарий для SKU ...».
- Сценарий неполон → «У шага “Получить фото” отсутствует переход после ответа», кнопка перехода к узлу.
- Вложение недоступно → «Не удалось открыть фото; повторите получение или передайте менеджеру».
- Ozon rate limit/сеть → «Синхронизация временно недоступна», если backend это подтверждает; показать возможность безопасной повторной проверки.
- Отправка имеет uncertain outcome → явно `Не удалось подтвердить отправку`, не дублировать без сверки.

Ошибки форм рядом с полем, ошибки узла прямо на схеме, ошибка отдельной реплики рядом с сообщением, проблемы подключения в `Настройки → Ozon`, общий audit в `Журнал`. Не выводить сырые stack traces, токены, payloads и технические коды как единственное объяснение. У manager нет доступа к глобальной диагностике.

## 8. Журналы и трассировка

Система обязана журналировать: начало/ошибку синхронизации, заказ, связывание позиции/чата, входящий message/event и dedup, выбранную версию сценария, переходы, заполнение/отклонение поля, прием файла, черновик/публикацию сценария, попытку отправки/подтверждение/ошибку, ручной takeover/return, изменение привязок, переход в ready, передачу брифа и ошибки. Типовые поля: timestamp, actor, seller_account, chat, item, scenario version, node, correlation ID, event, result, безопасные metadata. Секреты и лишние персональные данные не писать в stdout/audit.

Аудит доступен admin. Manager видит переписку и пользовательскую историю по чату, но не секреты, raw payloads и глобальные системные логи.

## 9. Готовый бриф и передача

Результат по каждой товарной позиции — структурированный объект:
- исходный Ozon order/posting/item context;
- внутренний тип товара;
- безопасные references на полученные фото;
- фон/пожелания для `portrait_background`;
- список фото (≤8), текст и дополнительные пожелания для `collage`;
- `template_id`, фото, пожелания для `template_art`;
- версия сценария, timestamps, completeness, факт подтверждения (если шаг включён);
- ошибки/нерешённые вопросы и признак `ready`.

Не помечать бриф готовым при недоступном обязательном медиа, пропущенном обязательном поле или неопределённом шаблоне. Передача дальше: в MVP внутренний статус `ready` + доступный admin экспорт/просмотр (конкретный формат экспорта согласовать). Автоматическая отправка в MES/CRM/Proof или другое производство — отдельный контракт. Не выдавать «готово к производству» за «картина готова».

## 10. Технические требования

- При новом репозитории стек утверждается отдельно; при внедрении в Bellenne One использовать существующий стек, авторизацию, очереди, хранилище и UI primitives. Не переписывать Pulse.
- `OzonAdapter`: версия API/аутентификация/чаты/заказы/медиа изолированы от доменной логики; нормализация данных и контракты тестируются через fixtures.
- `OrderIntake`, `ProductMapping`, `ScenarioEngine`, `ChatOrchestration`, `MediaService`, `BriefService`, `AuditService` — логические границы, не обязательные имена файлов или микросервисы.
- Периодическая синхронизация, если нет поддерживаемых push-событий; cursor/checkpoint, backoff, лимиты, неполные страницы, повторная сверка, диагностика и ручной resync у admin.
- Очередь для внешнего I/O; idempotent import, per-chat serialization, безопасная фиксация state + outbox, отслеживание отправок. Проверка manual mode непосредственно перед отправкой.
- Не хранить вложения без ограничения и проверки: допустимые MIME и размер определяются по реальным требованиям/лимитам, защита от path traversal, безопасное хранилище, политика очистки — открытый вопрос.
- Логи/метрики: число ошибок API, очередь sync/send, последние timestamps, причины отказов; это операционные диагностические метрики, не выдуманные бизнес-KPI.
- Конфигурация ключей: secrets/env/secret storage, rotate/revoke, доступ только admin; исключить утечку в frontend, логи, файлы экспорта.
- Не обещать определённый latency/throughput до нагрузочного тестирования; предусмотреть асинхронность и доступную диагностику.

## 11. Этапы реализации

**Этап 0 — feasibility:** проверить API Ozon и подписку, чат и медиа, связь с заказом, безопасность; договориться о неясных условиях. **Критерий:** документированный доступный контракт или чётко обозначенный blocker.

**Этап 1 — мастер подключения, базовая интеграция и роли:** аутентификация, admin/manager, кабинеты Ozon, синхронизация заказов/позиций, маппинг товаров, чтение чатов и вложений. **Критерий:** менеджер читает только чаты, админ видит причины ошибок и настраивает кабинет; одна и та же позиция не создаётся дублем.

**Этап 2 — минималистичный двухколоночный Inbox:** история сообщений, ответы, статус отправки, связанный контекст позиции, защита от неразрешённых действий. **Критерий:** поддерживаемое тестовое сообщение проходит через реальный API; нет повторной отправки при неопределённом результате.

**Этап 3 — обязательный node-based редактор сценариев:** UI создания узлов/связей, инспектора, правки текстов, проверки/предпросмотра/публикации, движок и версионирование, три стартовых сценария. **Критерий:** изменение текста или этапа через UI не требует редактирования исходников, опубликованная версия не меняет текущий диалог.

**Этап 4 — автоматизация сбора и handoff:** выбор сценария по позиции, сбор фото/текста/шаблона, правила валидации, ручной перехват, бриф `ready`. **Критерий:** все три товарных варианта проходят end-to-end на тестовом аккаунте/фикстурах, без конфликтов бота и менеджера.

**Этап 5 — аудит и эксплуатация:** полная событийная лента, ошибки/повторная синхронизация, тесты безопасности/восстановления, инструкция эксплуатации. **Критерий:** состояние каждого брифа воспроизводимо по журналу, сбои внешнего API не создают потерянные/двойные действия.

## 12. Приёмочные сценарии и тесты

1. Новый заказ на каждый из трёх товаров создаёт нужную позицию и правильный сценарий из product mapping.
2. Неизвестный SKU/неоднозначный чат не запускает случайный сценарий и попадает на разбор.
3. Повторно полученные order/message/event не создают второго диалога, брифа или отправки; отдельный законный новый заказ сохраняется.
4. Коллаж с 8 валидными фото принимается; 9-е фото корректно отклоняется/не включается с понятным пояснением; минимум проверяется согласно утверждённой настройке.
5. `template_art` не завершается без одного действующего template_id; два неоднозначных выбора требуют уточнения.
6. Отсутствующее/повреждённое обязательное фото не засчитывается, не позволяет перейти в `ready`.
7. Админ меняет текст/этап через UI и публикует v2; ранее начатый диалог остаётся на v1.
8. Менеджер берёт чат в ручное управление одновременно с запланированной отправкой бота: одно корректное сообщение, нет двойного ответа.
9. Ошибка/timeout Ozon оставляет отправку в проверяемом состоянии; возможный успешный ответ не дублируется без сверки.
10. Менеджер получает 403 на admin endpoints, configs, tokens, общие audit logs, чужие вложения/заказы по прямой ссылке.
11. Админ видит, какая версия сценария отправила какое сообщение, кто перехватил чат, какие поля были собраны и почему бриф готов/не готов.
12. Деактивация ключа, закрытие чата или отсутствие прав не маскируется фальшивым успехом; UI показывает ошибку без раскрытия секрета.
13. Отмена/изменение статуса внешнего заказа корректно обрабатывается по заранее согласованной политике и не вызывает неконтролируемой рассылки.
14. В истории/логе не видны API-ключи и чувствительные данные; медиа недоступны посторонним пользователям.
15. Страницы Folio используют общие компоненты Bellenne; существующие страницы Pulse визуально и функционально не изменены.

## 12.1 Дополнительные UI-приёмочные проверки v1.1

16. Admin проходит мастер Ozon по шагам, сохраняет промежуточное состояние, вводит Client ID/API key, видит замаскированный сохранённый ключ и может заменить его. Ни manager, ни frontend/API чтения не получает значение ключа.
17. Положительная проверка кабинета при отсутствии прав чатов показывает раздельные `кабинет доступен` и `чаты недоступны`; запуск бота заблокирован с понятной причиной, без тестовой отправки реальному покупателю.
18. Admin строит каждый из трёх сценариев **на canvas**: добавляет узел, соединяет два шага, редактирует текст, сохраняет, перезагружает страницу и видит ту же структуру и позиции узлов.
19. При удалённой обязательной связи/пустом тексте `Проверить` подсвечивает конкретный узел, показывает короткую причину и не разрешает `Опубликовать`; клик по проблеме выбирает узел и открывает инспектор.
20. Dry-run проходит ветки на тестовых сообщениях и медиа, показывает заполненные поля и не вызывает Ozon send API. Публикация v2 не изменяет уже начатый диалог на v1.
21. Manager видит только минималистичный двухколоночный Inbox, открывает заказ через drawer и отвечает вручную. Не видит Ozon keys, builder, users или audit даже через прямой URL/API.
22. На узком экране чат-лист, переписка и drawer доступны без постоянной третьей колонки; длинные сообщения, файлы и статусы не ломают layout.
23. Ошибки конфигурации, недоступного фото и неопределённой отправки показаны в соответствующем контексте и содержат действие пользователя; слепого повтора неизвестно отправленного сообщения нет.
24. Все три основных раздела настроек сохраняются раздельно: изменение узла сценария не требует пересохранения ключей Ozon; изменение подключения не сбрасывает product mapping.

## 13. Открытые решения — согласовать ДО автоматизации

1. Какая схема Ozon используется: FBO/FBS/rFBS? Какая подписка и есть ли доступ к chat API в конкретном кабинете? Можно ли инициировать чат и получать именно фото?
2. Товар «картина + замена фона»: сколько фото обязательно, обязателен ли пример нового фона или достаточно описания?
3. Коллаж: минимальное число фото (технический максимум — 8), требуется ли текст всегда, есть ли порядок фотографий и лимит символов?
4. Шаблоны: где хранится каталог, как выглядят изображения-превью, можно ли выбрать любой из N или только разрешённые для SKU?
5. Требуется ли подтверждение сводки покупателем? Что делать при молчании, отмене заказа или смене пожеланий после `ready`?
6. Инициировать переписку автоматически для всех заказов или только если чат уже существует/доступен? Частота сообщений и политика напоминаний?
7. Если один чат относится к нескольким позициям/заказам, как определяется активный контекст? Допустимо ли разделение по сообщениям?
8. Нужны ли менеджерам все чаты или назначенные? Разрешено ли менеджеру возвращать бота автоматически?
9. Куда передавать бриф после `ready` (внутренний экспорт, MES, другая система), в каком формате и кто подтверждает готовность?
10. Какой стек/репозиторий используется, какая уже есть система авторизации и файлового хранения? Не выбирать новый стек без осмотра проекта.
11. Каковы требования к срокам хранения фото/переписки, доступу и удалению, а также правилам обработки данных покупателя? Утвердить перед запуском.
12. Утверждён ли отдельный Folio Product Accent? Пока использовать общую палитру Bellenne.

**Правило для Codex:** пункты выше являются решениями, а не разрешением самостоятельно придумать ответы. Если препятствуют разработке — обозначь конкретный blocker и запроси решение; остальное делай независимо от него.

# Folio ↔ FolioImageWorker

Folio хранит очередь заданий. Когда сценарий доходит до блока «Создать макет через воркер», он ставит в очередь 1–8 фотографий из брифа, описание обработки и размер в сантиметрах. Размер берётся из окончания артикула, например `КАРТЕСТ-01_40х60`; если его нет, используется 40×60 см.

**Воркер сам опрашивает Folio** по публичному HTTPS-адресу. Folio не обращается к адресу ПК, поэтому VPN и смена IP ПК не нарушают связь. Один воркер обрабатывает по одному заданию; пока результат не подтверждён, Folio повторно выдаёт тот же ID. Воркер отправляет состояния и готовый JPEG в Folio с повторными попытками при сетевой ошибке.

## Настройка

1. В BellenneOne укажите `FOLIO_PUBLIC_BASE_URL=https://<публичный-домен>` и разверните новую версию приложения и gateway.
2. В Folio → **Настройки → Воркер изображений** скопируйте полную ссылку для опроса в Windows-приложение воркера. Настройте там общий ключ и подключение AI Tunnel.
3. В Folio введите только тот же ключ. Адрес ПК не нужен. Запустите воркер на ПК. Последний запрос воркера появится на странице настроек.

Gateway пропускает `GET /folio/image-worker/next`, `POST /folio/image-worker/jobs/{id}` и `GET /folio/image-worker/input/{token}/{index}` без браузерной сессии. Первые два метода проверяют `Authorization: Bearer <общий ключ>`, ссылка на фото защищена случайным токеном. Дополнительные заголовки возможностей не требуются. Старые webhook и callback-маршруты возвращают 410.

В Windows-приложении настраиваются две отдельные папки: рабочая (оригиналы, `generated.png`, `preview.jpg`, очередь и логи) и папка готовых печатных JPG (локальная или UNC). Core не управляет этими папками. Печатный JPG содержит метаданные 150 DPI, зеркальные края и белые поля. В Folio передаётся только его путь. `preview.jpg` содержит только видимую часть, ровно 1000 пикселей по длинной стороне; Folio сохраняет его в собственном медиахранилище.

## Контракт очереди

`GET /folio/image-worker/next`: 204 при пустой очереди; иначе JSON с `id`, `worker_id`, `prompt`, `model`, `prompt_mode`, `width_cm`, `height_cm`, `image_urls`. Последнее поле содержит 1–8 HTTPS-ссылок в порядке фото брифа. ID закрепляются в БД при выдаче; повторный опрос и перезапуск Core не создают новое задание. Воркер также должен сохранять выполнение по этим ID, не запускать генерацию повторно после потери ответа.

`POST /folio/image-worker/jobs/{id}`: multipart-поля `worker_id`, `status`. Статусы: `queued`, `generating`, `composing`, `completed`, `failed`, `unknown`. Для `completed` обязательны `print_file` с расширением `.jpg`/`.jpeg` и JPEG-файл `preview`. Для `failed`/`unknown` передаётся `error`. Повтор завершения идемпотентен; другое терминальное состояние отклоняется.

`unknown` сохраняет неопределённость платного запроса: задание не выдаётся повторно на генерацию. Сценарий остаётся ждать; воркер может доставить найденный результат с прежними ID. `failed` продолжает ветку ошибки. Старые состояния в БД сохраняются для совместимости, но не принимаются как новые статусы протокола.

Для передачи заказа в MES Core читает печатный JPG через настроенное сопоставление UNC-корня с примонтированной папкой и сохраняет его в папку производства. В MES уходит только JSON, не файл (см. `FOLIO_LARAVEL_WEBHOOK_CONTRACT.md`). Без доступного сопоставления/файла передача не выполняется.

После блока «Создать макет через воркер» можно добавить блок **«Отправить макет»**. Он отправит сохранённое превью покупателю через Ozon и продолжит сценарий после подтверждения отправки. При ошибке генерации срабатывает ветка ошибки блока создания макета.

Подробные поля запросов и ответов описаны в `BellenneFolioImageWorker/API_CONTRACT.md`.
